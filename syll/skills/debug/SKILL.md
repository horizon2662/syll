# 系统性调试

当用户报告 bug、程序报错、或行为不符合预期时，按此流程操作。

## 第一步：复现

- 运行出问题的命令或代码
- 记录完整的错误输出（不要只看最后一行）
- 如果错误不可复现，问用户具体的操作步骤

## 第二步：定位

从错误信息出发，逐步缩小范围：

1. **读错误堆栈** — 从最后一行往上看，找到你自己写的代码（不是第三方库的内部调用）
2. **定位文件和行号** — 读取对应文件的那一行及周围上下文
3. **检查直接原因** — 变量值是什么？类型对不对？是否为 None/undefined？
4. **如果直接原因不明显** — 在可疑位置加 print/log，重新运行观察

## 第三步：分析根因

常见的根因模式：

| 症状 | 可能原因 |
|------|---------|
| TypeError: NoneType | 函数返回了 None 而不是预期值 |
| KeyError / AttributeError | 字典/对象的键名拼写错或数据结构变了 |
| ImportError / ModuleNotFoundError | 依赖没装或路径不对 |
| 语法对但结果错 | 逻辑错误：off-by-one、条件反了、变量覆盖 |
| 间歇性失败 | 并发/竞态、时序依赖、外部服务不稳定 |
| 改了代码但没生效 | 改错文件了、缓存没清、热更新没触发 |

## 第四步：修复

- **最小化修复** — 只改必要的部分，不要顺便"重构"
- **如果修复范围较大**，先向用户说明计划，获得同意后再改
- 修复代码写注释说明为什么这样改（特别是非显而易见的情况）

## 第五步：验证

- 重新运行出问题的命令，确认错误消失
- 如果有相关测试，运行测试确认没有引入新问题
- 如果修复可能影响其他功能，检查相关模块

## 第六步：记录

将调试结果写入 memory：
- 症状和根因
- 修复方法
- 如何避免类似问题（如果适用）
