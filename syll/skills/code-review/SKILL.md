# 代码审查

当用户要求 review 代码、检查 PR、或说"帮我看看这段代码有没有问题"时，按此流程操作。

## 审查维度

### 1. 正确性（最高优先级）
- 逻辑是否正确？边界情况处理了吗？
- 空值/None/undefined 有没有防护？
- 异步操作是否有正确的 await/Promise 处理？
- 并发场景有没有竞态条件？

### 2. 安全性
- 用户输入有没有做验证和清洗？
- SQL 查询是否用了参数化（防注入）？
- 敏感信息（密码、API key）有没有硬编码？
- 文件路径有没有做路径遍历防护？

### 3. 错误处理
- try/except 或 try/catch 范围是否合理？
- 错误信息是否有意义（不要只写 "error"）？
- 是否有静默吞异常的情况（空的 except 块）？

### 4. 风格与可读性
- 命名是否清晰？（变量名表达意图）
- 函数长度是否合理？（一个函数做一件事）
- 有没有重复代码可以提取？
- 注释是否有价值？（解释"为什么"而不是"做了什么"）

### 5. 性能（低优先级，除非明显有问题）
- 循环内是否有不必要的重复计算？
- 数据库查询是否可以批量处理？
- 大列表操作是否可以用生成器？

## 输出格式

```
## 审查结果

### 🔴 必须修复（正确性/安全性问题）
- [文件:行号] 问题描述 → 建议修复方式

### 🟡 建议改进（风格/可维护性）
- [文件:行号] 建议内容

### 🟢 值得肯定
- 做得好的地方
```

## 注意

- **只审查被要求审查的部分**，不要越界
- 发现问题时要给出具体的修复建议，不只是说"这里有 bug"
- 如果代码量大，按模块分批审查
